# Hermes Enhancer v0.22.x Architecture Design

## Current v0.21.0 Architecture (Frozen Baseline)

### Core Components

**FederatedDB**: SQLite WAL-mode persistence with batched async writes
- Bounded in-memory queue (maxsize=5000)
- Background batch worker
- Transaction-per-batch persistence
- Retry with exponential backoff [0.0, 0.5, 1.5s]
- Lifecycle counters (events_enqueued/persisted/dropped/failed/retried)
- Graceful shutdown: stop → drain → flush → commit → worker exits
- Async APIs: async_push(), async_get_recent(), async_count(), async_summary_counts(), async_prune()
- Sync APIs: push(), get_recent(), count() (backward compatible)
- Anomalous duration filtering (≤0 or >300s flagged)
- Auto-pruning when sync_queue exceeds prune_threshold (default 5000)
- Summary analytics aggregation

**HermesEnhancer**: Core orchestrator
- pre_tool_call / post_tool_call hooks
- Tool name extraction from args/kwargs
- Anomaly detection (_flag_anomalous)
- Memory monitoring and self-heal
- PredictivePreload: Markov chain tool sequencing
- MetaLearner: Winning workflow storage
- SkillGraph: Dependency graph with SQLite persistence
- SkillComposer: Workflow orchestration with conditional branches and retry

**Learning Systems**
- MetaLearner: History optimization, workflow summaries
- SkillGraph: Zero cold-start via SQLite persistence
- SkillComposer: Conditional execution, retry/backoff
- PredictivePreload: Pattern-based anticipatory loading
- FeedbackOptimizer: EMA success scoring with anomaly exclusion

**Telemetry**
- Lifecycle counters tracked
- event_id, trace_id, tool_call_id per event
- EMA scoring excluded anomalous durations
- Sync ≈ persisted + dropped + failed (approximately)

**Queue**
- FIFO queue with maxsize=5000
- Background worker processes batches of 100
- Backpressure: enqueue_event returns None when full
- events_dropped counter observable

## Durability Gaps (v0.21.0 → v0.22.x)

The following gaps identify why v0.21.0 received "READY WITH WARNINGS":

1. **No persistent buffer**: Events in queue lost on crash (no durable state between process runs)
2. **No crash recovery**: No startup recovery mechanism
3. **No duplicate prevention**: No UNIQUE constraint on event_id at DB level
4. **No corruption detection**: PRAGMA integrity_check only on connection open, not systematic
5. **No persistent retry state**: attempt_count, next_retry_at lost on restart
6. **No idempotent persistence**: Same event_id could theoretically be re-inserted
7. **No buffer state machine**: No explicit states tracking event durability progress
8. **No disk-space handling**: Buffer grows unbounded if not managed
9. **No failure injection testing**: No deterministic way to test crash scenarios
10. **No recovery matrix**: No documented behavior for each failure scenario

## Proposed v0.22.x Architecture

### 1. Persistent Event Buffer

A durable SQLite table (`event_buffer`) sits between event creation and final persistence.

**Schema (proposed):**
```sql
CREATE TABLE IF NOT EXISTS event_buffer (
    event_id TEXT UNIQUE NOT NULL PRIMARY KEY,
    trace_id TEXT NOT NULL,
    tool_call_id TEXT,
    event_type TEXT NOT NULL,
    payload TEXT NOT NULL,
    created_at TEXT NOT NULL,
    state TEXT NOT NULL DEFAULT 'CREATED',
    attempt_count INTEGER NOT NULL DEFAULT 0,
    last_error TEXT,
    next_retry_at TEXT,
    buffered_at TEXT NOT NULL,
    persisted_at TEXT,
    schema_version INTEGER NOT NULL DEFAULT 1,
    checksum TEXT
);
```

**Rationale**: Using the existing SQLite database for the buffer is the simplest reliable architecture. It leverages SQLite's built-in durability (WAL mode, journaling) without introducing a separate persistence layer. The UNIQUE constraint on event_id provides idempotency.

Alternative considered: Separate embedded database. Rejected: Adds complexity of separate file management, recovery coordination, and synchronization. Using the existing DB is simpler and justifiable since:
- Same process, same filesystem
- Same WAL mode guarantees
- No network dependency
- Simpler recovery (single DB to replay)

### 2. Buffer State Machine

Explicit states tracking durability progress:

```
CREATED
  ↓ (prepared/buffered)
BUFFERED
  ↓ (queued_for_persistence)
QUEUED
  ↓ (write_in_progress)
PERSISTING
  ↓ (commit_successful)
PERSISTED

Failure transitions:
PERSISTING  → FAILED (write error, lock timeout)
FAILED      → RETRY_WAIT (backoff period)
RETRY_WAIT  → QUEUED (retry attempt)
RETRY_WAIT  → FAILED (max attempts exceeded)

Crash/restart:
BUFFERED    → RECOVERY (startup recovery identifies incomplete events)
RECOVERY    → QUEUED (re-enqueue validated incomplete events)

Critical invariant:
If state = DURABLY BUFFERED (or PERSISTED),
crash recovery must not lose the event.
```

### 3. Durability Semantics

Clear distinctions:

- **CREATED**: Event object in memory, not written to DB. Not crash safe.
- **BUFFERED**: Event written to `event_buffer` table, transaction committed. Durably buffered if the DB transaction committed according to WAL mode guarantees.
- **PERSISTED**: Event also exists in final event table (sync_queue or dedicated events table) after successful commit. The buffer entry may be kept or removed per policy.
- **FAILED**: Persistence attempt failed after retries. Event remains in buffer for possible recovery.

**What each state means concretely:**

| State | Written to buffer DB? | Written to final event DB? | Survives process crash? |
|---|---|---|---|
| CREATED | No | No | No |
| BUFFERED | Yes (committed) | No | Yes (event in buffer, may be recovered) |
| PERSISTED | May remain or be removed | Yes (committed) | Yes (event in both buffer and final DB) |
| FAILED | Yes | No | Yes (event in buffer, will be retried/recovered) |

### 4. Recovery Algorithm

On application startup, execute:

1. `open_database()` — with WAL mode recovery
2. `verify_database_health()` — PRAGMA quick_check + integrity_check
3. `inspect_persistent_buffer()` — find events in BUFFERED/PERSISTING/FAILED states
4. `identify_incomplete_events()` — events not marked PERSISTED
5. `validate_buffer_records()` — check schema_version, checksum integrity
6. `check_final_database()` — find events already in sync_queue/events table
7. `recover_pending_events()` — re-enqueue validated incomplete events
8. `restore_retry_state()` — preserve attempt_count, next_retry_at from buffer
9. `enqueue_recoverable_events()` — queue events for bounded batch persistence
10. `expose_recovery_metrics()` — report recovered/skipped/failed counts

**Deterministic**: Same input → same recovery outcome.

### 5. Idempotency

**UNIQUE constraint on event_id** in the event_buffer table:

```sql
CREATE TABLE IF NOT EXISTS event_buffer (
    event_id TEXT UNIQUE NOT NULL PRIMARY KEY,
    ...
);
```

**Final persistence table** (e.g., sync_queue or events table) also uses event_id as unique:

```sql
-- Idempotent insert attempt
INSERT OR IGNORE INTO sync_queue (..., event_id, ...)
VALUES (..., 'abc123', ...)
```

**Behavior**: If INSERT OR IGNORE finds event_id already exists, it silently does nothing. No duplicate created. A telemetry counter `duplicates_prevented` is incremented.

### 6. Retry Persistence

Persisted across restarts in the buffer:

```sql
-- In event_buffer
attempt_count INTEGER NOT NULL DEFAULT 0
last_error TEXT
next_retry_at TEXT NOT NULL
```

**Bounded exponential backoff**:
- Attempt 1: 1 second
- Attempt 2: 2 seconds
- Attempt 3: 4 seconds
- Attempt 4: 8 seconds
- ...
- Max attempts: 5 (configurable)

**Do not reset retry count to zero after restart**. The attempt_count from the buffer is preserved.

### 7. Database Health

```python
def verify_database_health(db):
    """Check SQLite integrity and health."""
    conn = db._get_conn()
    try:
        # Quick check first
        result = conn.execute("PRAGMA quick_check").fetchone()[0]
        if result != 'ok':
            # Full integrity check
            result = conn.execute("PRAGMA integrity_check").fetchone()[0]
            if result != 'ok':
                logger.error("Database corruption detected: %s", result)
                return False

        # Check for hot pages / WAL issues
        wal_status = conn.execute("PRAGMA wal_checkpoint").fetchone()

        return True
    except sqlite3.DatabaseError as e:
        logger.error("Database health check failed: %s", e)
        return False
    finally:
        conn.close()
```

**States distinguished**:
- healthy: quick_check = ok, integrity_check = ok
- degraded: quick_check != ok but integrity_check = ok
- locked: busy_timeout exhausted
- unavailable: database file not accessible
- corrupted: integrity_check != 'ok'

**If corruption detected**: Surface error clearly. Do NOT silently delete or recreate.

### 8. Disk Space Protection

Define behavior tiers:

- **normal**: Buffer operates normally, auto-pruning at threshold (default 5000)
- **low disk**: Reduce prune_threshold, surface warning via telemetry
- **critical disk**: Surface error, do not accept new events into buffer, drain existing
- **write failure**: DB exception → events_failed counter → recovery path

Never silently discard durable events. If an event must be dropped due to resource limits, record why via `events_dropped` with reason metadata.

### 9. Telemetry Extensions

New counters to expose:

```
events_created         → total events ever created
events_buffered        → events in persistent buffer (not yet finalized)
events_recovered       → events recovered on startup from buffer
events_replayed        → events re-sent for persistence after recovery
events_persisted       → events durably in final DB
events_failed          → events that failed after max retries
events_retried         → total retry attempts across all events
events_dropped         → events dropped (queue full, disk full, policy)
duplicates_prevented   → INSERT OR IGNORE hits existing event_id
buffer_corruptions     → detected corrupt buffer records
recovery_failures      → events that could not be recovered
db_integrity_failures  → PRAGMA integrity_check failures
```

**Distinguish event counts from operation counts**:
- 1 event with 3 retry attempts ≠ 3 events persisted
- Counter reconciliation after flush() and after recovery must be explicit

### 11. Concurrency Safeguards

Validate scenarios:
- Multiple producers writing to event_buffer
- Background worker reading from buffer
- Async producers enqueuing events
- Recovery worker processing incomplete events
- SQLite locking behavior (busy_timeout=5000)
- Concurrent writes with WAL mode
- Duplicate replay prevention (UNIQUE constraint)
- Shutdown during active persistence

**No race condition should allow**:
- Event loss
- Duplicate event (event_id)
- Buffer deletion before commit
- Counter corruption

### 11. Failure Injection Testing

Disable by default in production. Enable via environment variable or config flag.

Test at minimum:
- buffer write failure (simulated DB write error)
- buffer commit failure (simulated transaction rollback)
- database lock (block writer, verify retry)
- database unavailable (simulated file lock)
- database transaction failure (exception during INSERT)
- worker interruption (thread killed mid-processing)
- process interruption (process killed at various points)
- duplicate event (INSERT OR IGNORE test)
- corrupted buffer record (malformed schema_version)
- shutdown interruption (shutdown during buffer flush)

### 12. Crash Test Matrix

| Scenario | Expected | Data-loss Risk | Duplicate Risk |
|---|---|---|---|
| crash before buffer commit | event may be absent (durability not confirmed) | Possible | No |
| crash after buffer commit | event recovered on restart | No | No |
| crash before final DB commit | event recovered (in buffer) | No | No |
| crash after final DB commit | no duplicate (UNIQUE) | No | No (if UNIQUE enforced) |
| crash before buffer cleanup | recovery detects already persisted | No | No |
| DB locked | retry with backoff | No | No |
| DB unavailable | retry/recover | No | No |
| transaction failure | event retained in buffer | No | No |
| malformed buffer record | observable failure | Possible | No |
| duplicate event | no duplicate (UNIQUE) | No | No |
| worker interruption | pending events survive | No | No |
| shutdown interruption | recover on restart | No | No |

### 13. Performance Considerations

Benchmark against v0.21.0:

| Metric | v0.21.0 | v0.22.x (target) | Delta |
|---|---|---|---|
| single push | ~321 µs | ~350 µs | +9% (buffer overhead) |
| batch push (5K) | ~5.5 ms | ~6.0 ms | +9% |
| async_push | functional | functional | unchanged |
| flush | functional | functional | unchanged |
| startup (with recovery) | ~same | ~+20ms | recovery cost |
| memory | ~5.2 MB | ~5.5 MB | +6% (buffer state) |

**Do not weaken durability guarantees for performance**. Document any regression.

### 14. Known Limitations (v0.22.x)

1. **No physical power-loss durability**: If power is removed during a DB write that hasn't fsynced, data may be lost. This is SQLite limitation, not architecture flaw. Claim only process-crash durability.
2. **No multi-process concurrent write guarantee**: Only one writer process should use the DB. Multiple processes reading is fine.
3. **Buffer growth**: Without auto-pruning, buffer grows. Pruning policy: only remove PERSISTED entries older than retention period (configurable, default 14 days).
4. **Recovery time**: Startup recovery time scales with number of incomplete events. Bounded processing (batch by 100) prevents long startup delays.
